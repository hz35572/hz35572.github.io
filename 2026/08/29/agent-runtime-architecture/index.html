在现有业务系统中集成 Agent 能力：Agent Runtime 架构设计方法与最佳实践

在现有业务系统中集成 Agent 能力：Agent Runtime 架构设计方法与最佳实践

本文分享一套在现有业务系统中新增 Agent 能力的架构设计方法。它不依赖任何 Agent Framework，通过 Supervisor + ReAct 主循环和 Tool / SubAgent / Skill 三模块解耦，实现”核心 Runtime 稳定、能力无限扩展”。文末给出可落地的分阶段实施建议。

一、问题背景：业务系统需要 Agent，但不想被 Agent 绑架

越来越多的业务系统开始接入 LLM 能力。一开始只是简单的问答，很快需求就演变成：

  • 多步推理：用户问”分析最近 30 天退款率为什么上升”，这需要查询数据、执行分析、组织结论，不是一次 LLM 调用能解决的；
  • 工具调用：Agent 需要查订单、调 HTTP 接口、执行 SQL；
  • 任务委托：复杂分析任务应该交给”专业的 Agent”去做，而不是让主 Agent 什么都干；
  • 知识注入：Agent 需要按专业规范做事，比如”关键事实需要独立来源交叉验证”。

面对这些需求，一个自然的选项是引入 LangChain、AutoGen 这类 Agent Framework。但在很多现有业务系统中，这条路并不合适：

  1. 框架侵入性太强：Agent Framework 通常要求你按它的抽象来组织代码，与现有业务 Service 层的整合成本高；
  2. 黑盒循环难以治理：生产系统需要权限控制、成本预算、链路追踪、错误治理，框架内置的循环往往很难深度定制这些能力；
  3. 升级风险不可控：业务系统的核心诉求是稳定，而框架的 API 变动频繁。

所以问题是：能否自己设计一个轻量、稳定、可治理的 Agent Runtime，既满足当前需求，又为未来扩展留足空间？

这是典型的开闭原则（Open-Closed Principle）在 Agent 架构上的应用：对扩展开放，对修改关闭。下文将展开这套架构的完整设计。

二、核心架构原则

在讨论具体模块之前，先确立三条贯穿全局的架构原则。它们是所有后续设计的出发点。

2.1 原则一：Supervisor 负责全局决策，不负责具体执行

Supervisor 是全局 ReAct 主控 Agent，每一轮它需要回答：

对应地，Supervisor 会做四类决策：直接回答、调用 Tool、委托 SubAgent、加载 Skill。

但 Supervisor 明确不做这些事：

  • 不实现具体业务 Tool 的逻辑；
  • 不介入 SubAgent 内部的执行过程；
  • 不负责权限、安全、重试、幂等等基础治理（这些是 Runtime 的职责）；
  • 不直接访问 DB、HTTP、文件和业务 Service——所有业务能力统一通过 Tool 暴露。

这条原则的价值在于：Supervisor 的 Prompt 和决策逻辑可以保持精炼，不会随业务膨胀而腐化。

2.2 原则二：Runtime 负责循环，不负责业务能力

2.3 原则三：Tool、SubAgent、Skill 三模块独立

这是整套架构最关键的概念区分，也是实践中最容易混淆的地方：

Skill 按需加载的专业指导 否 注入方法、规范、知识和指令

三、总体架构

3.1 架构全景图

从上到下可以分为四层：

  1. 接入层：现有应用通过 AgentService 调用 Agent 能力，对业务侧来说就是一个普通服务；
  2. 核心循环层：ReactExecutor 驱动 Supervisor ReAct，通过 LLM Gateway 与模型交互；
  3. 分发层：ToolCallDispatcher 将模型产生的 Tool Call 分发到三个模块；
  4. 能力层：Tool / SubAgent / Skill 三个完全独立的模块，各自拥有 Registry / Service / Provider / Executor 的分层结构。

Local Provider 的实现揭示了两个重要机制——上下文隔离和预算分配：

  • 子 Agent 获得新的 Child Context，默认继承 request_id / trace_id / user_id / tenant_id / permissions / services / deadline，但不继承 Supervisor 的全量 message history 和原始 Tool Result；
  • 子预算从父预算中分配，子 Agent 不能拥有完整预算，防止成本失控。

另一个关键设计是 SubAgent Catalog：Supervisor 只看到每个 SubAgent 的 name + description，不看到完整内部 Prompt。这既节省 Context，也避免了 Prompt 相互干扰。

五、生产级治理能力

Demo 到生产之间隔着一系列治理能力。这些能力不是可选项，而是 Agent 系统上线的必要条件。

5.1 Context 与上下文隔离

ExecutionContext 携带请求级元数据，由 Runtime 控制，不能由 LLM 构造：

Supervisor 委托 SubAgent 时通过 create_child() 创建子上下文，只传递必要信息（task、facts、artifact references），不传递全量历史。

5.2 Artifact Store 与 State Reducer：对抗 Context 膨胀

大量数据（10000 行 SQL 结果、网页全文、复杂 JSON）不应直接进入 ReAct Context。统一存入 Artifact Store，State 只保留引用和摘要：

5.3 Execution Budget：成本与执行边界

SubAgent 从父预算中分配子预算。没有 Budget 的 Agent 系统等于一张没有额度的信用卡。

5.4 权限与安全：双层检查 + 幂等

Tool 风险分级：

权限采用双层设计：

  • 第一层（Catalog / Resolver）：不向模型暴露无权限的能力——模型看不到的能力就不会尝试调用；
  • 第二层（Executor 执行前）：最终执行前再次检查，防止 Prompt 注入或其他手段绕过。

对于有副作用的 Tool，必须考虑”timeout → retry → duplicate side effect”链路，通过稳定的 idempotency_key 保证幂等。

7.3 需要重点控制的五个风险

风险一：Tool 数量膨胀。 不能永远把所有 Tool Schema 暴露给 Supervisor。当 Tool 数量增长到几十个以上，应依次引入 Permission Filter → Catalog Filtering → Top-K Retrieval → Semantic Retrieval。

风险二：SubAgent 无限递归。 第一版建议强制限制委托层级为 Supervisor → SubAgent → Tool / Skill，普通 SubAgent 默认不继续委托其他 SubAgent。

风险三：Skill 越界。 Skill 只应包含 Instruction / Knowledge / Rules / Examples。如果某个”Skill”需要真正执行代码，它应该是 Tool 或 SubAgent。

风险四：Context 膨胀。 大结果进 Artifact Store，历史通过 State Reducer 压缩。前面已有详述，此处强调：这两个机制应在 P1 尽早落地，不要等到线上出现成本事故。

风险五：高风险动作仅靠 Prompt 控制。 Prompt 约束对注入攻击是脆弱的。高风险动作必须在 Runtime 层实现 Permission / Policy / Approval / Idempotency / Audit，Prompt 只是第一道防线，永远不是最后一道。

八、总结

这套架构最终收敛为一张图：

三个模块的最终定义：

回顾整套设计的核心思想：

  1. 决策与执行分离：Supervisor 只做全局决策，Runtime 只管循环，业务能力全部下沉到 Tool / SubAgent / Skill；
  2. 协议统一，实现解耦：模型侧只认识 Tool Calling，内部三模块独立演进；
  3. 治理内建，而非外挂：Budget、权限、Tracing、错误模型、幂等由 Runtime 层统一提供，业务开发者无需关心；
  4. 扩展不侵入：新增能力只扩展各自模块的 implementations/，核心循环代码保持稳定。

如果你正在评估是否在现有系统中引入 Agent 能力，希望这套架构能给你一个参考：Agent 能力不是一个框架的引入，而是一个边界清晰的小型 Runtime 的设计。把循环、能力、治理三件事分开，系统就能在保持稳定的同时无限扩展。
