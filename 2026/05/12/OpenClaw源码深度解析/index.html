一、OpenClaw 是什么？它解决了什么问题

OpenClaw 不是一个 AI 模型，而是一个 AI Agent 运行时框架（Runtime Framework）。它坐在 AI 模型和外部世界中间，负责将自然语言指令转化为真实的系统操作。

用一句话概括：

OpenClaw = Gateway（网关） + Agent Runtime（运行时） + Skills（技能） + Memory（记忆）

传统聊天机器人只停留在”交互层”——你问一句，它答一句。OpenClaw 要做的是从交互层跨越到”执行层”：让它能操作文件系统、执行命令、调用 API、管理日程、控制智能家居——真正替人干活。

自建一个这样的系统需要解决的问题清单长得让人望而却步：

OpenClaw 把这些全部搞定了。它的核心价值主张是：一套 AI Agent，接入所有渠道，支持定时任务、子 Agent 编排、多模态理解，所有数据留在你自己的设备上。

二、设计哲学：为什么它长得像一个操作系统

OpenClaw 的工程形态由以下几个核心设计哲学决定，这些理念写进了 VISION.md，贯穿整个代码库：

理念 含义
Local-first 本地优先，数据不离开用户设备，隐私安全
网关而非框架 不是 SDK/库，而是独立运行的控制平面
模型无关 支持 Claude、GPT、Gemini、DeepSeek 等任意 LLM
插件化内核 Skills、Channels、Providers 均可热插拔
CLI 优先 以命令行作为第一入口，便于直接调用系统能力
安全显式 强默认不阉割能力，把危险路径暴露为操作者可控开关

这套哲学直接决定了仓库形态：一个以”控制面 Gateway + 可插拔 Provider/Channel + 会话/上下文引擎”为骨架的编排系统，而不是一个”大而全的 Agent 框架”。

命名含义

  • Claw：龙虾钳子，象征”抓取、操控与执行”能力
  • Open：完全开源（MIT 协议），社区驱动
  • 项目前身：Warelay → Clawdbot → Moltbot → OpenClaw

三、仓库结构与工程形态

OpenClaw 是一个 TypeScript ESM monorepo，使用 pnpm workspaces 管理。项目规模超过 14,900 个文件、500+ 分支，是典型的作者驱动型大型项目。

代码仓库有严格的分层纪律。从 AGENTS.md 可以读出：

  • Core（src/**）必须对扩展不可知，不能为某个 bundled plugin 写特殊情况
  • Extension 只能通过 plugin-sdk、manifest 和注入的 runtime helpers 跨越边界
  • 扩展禁止深入 src/** 或其他扩展的内部
  • Gateway protocol 改动视为契约变更，需要向后兼容、版本化

这些硬边界通过 lint 规则、架构门（pnpm check:architecture）、import-cycles、TS 项目引用等机制来实际落地。

四、五层服务架构：从消息接入到任务执行

OpenClaw 的源码实现了清晰的五层服务分层，每一层职责分明、松耦合。

4.1 渠道适配层（Channel Adapter）

源码位置：src/channels/、src/slack/、src/telegram/ 等

渠道适配层的核心职责是协议适配。把 Discord、Telegram、WhatsApp、钉钉、飞书等不同平台的输入转成统一消息格式，同时提取附件。

源码中，每个通道都是一个独立的插件，必须实现统一的 ChannelPlugin 接口：

这种设计的精妙之处在于：核心模块不面向任何具体 IM 编程，只面向接口编程。无论未来出现什么新的 IM 工具，只要实现这套接口，就能无缝接入 OpenClaw 生态。

目前 OpenClaw 内置支持 8 个核心通道，通过插件系统支持超过 50 个扩展通道，覆盖 WhatsApp、Telegram、Discord、Slack、Signal、iMessage、飞书、钉钉等主流平台。

4.2 网关服务层（Gateway Server）

源码位置：src/gateway/

Gateway 是整个 OpenClaw 的核心服务，作为一个常驻的 Node.js 进程（监听在 127.0.0.1:18789），承担着：

  • 路由：根据消息来源分配给对应的 Agent
  • 会话管理：为每个用户-渠道组合创建独立的 Session，维护其状态
  • 车道队列（Lane Queue）：实现”车道式”队列，确保指令按序执行
  • 鉴权：WebSocket 连接挑战验证，防止恶意连接
  • 实时流式反馈：通过 WebSocket 将执行进度低延迟推送给客户端
  • 协议转换：统一处理 HTTP/WebSocket 三种消息类型（req/res/event），通过 TypeBox Schema 进行严格数据校验

4.3 Agent Runner 智能体运行器

源码位置：src/agents/

Agent Runner 是 AI 能力的承载者和执行引擎，核心功能包括：

  • 动态提示词构建：在运行时，根据 SOUL.md（灵魂/性格）、TOOLS.md（工具集）、AGENTS.md（角色）和会话历史，动态拼接出发送给大模型的完整提示词
  • 模型调用与容错：自动选择并调用配置的大模型，若主模型失败，能自动降级到备用模型或切换 API 密钥
  • 上下文窗口守护：监控会话长度，当接近模型上下文上限时，自动触发内容压缩或优雅终止

4.4 Agent Runtime 执行循环

源码位置：src/agents/pi-embedded-runner/

OpenClaw 采用了创新的 Lobster 智能体循环模式，包含四个核心步骤：思考（Think）→ 执行（Act）→ 观察（Observe）→ 反馈（Reflect）。

具体流程：

  1. 获取或创建 session lock（避免并发冲突）
  2. 构建 prompt（包括 system 提示和用户输入的清洗）
  3. 调用 LLM（流式返回）
  4. 如果遇到 tool call，交给 tool-policy-pipeline.ts 做安全检查：文件系统访问限制、循环检测、白名单过滤
  5. 非主会话的 tool 调用会丢进 Docker 沙箱执行（主会话走 host）
  6. 结果回来后做输出过滤，再返回给 LLM 或直接回复用户

4.5 记忆与技能层（Memory & Skills）

源码位置：src/memory/、skills/

这是 Agent 的长期记忆和能力扩展系统，将在第五节详细展开。

5.3 记忆系统：文件即真相

OpenClaw 的记忆系统是它最被行业称道的设计。它没有跟风堆复杂的 RAG 架构，而是回归最朴素的逻辑：把记忆当成普通的 Markdown 文件，文件才是真相的唯一来源。

为什么不用向量数据库

市面上大多数 Agent 框架的记忆方案存在几个致命问题：

  1. 黑盒向量数据库：记忆完全不可控，无法直接编辑、审查
  2. 强依赖云端服务：隐私与可用性全看别人脸色
  3. 没有分层设计：重要信息和无关内容混在一起，检索时关键信息被淹没

OpenClaw 反其道而行：以 Markdown 文件为记忆的唯一真相源，SQLite 为索引加速层，完全本地运行，人类可完全掌控。

这意味着：

  • 你可以用任何编辑器直接打开文件修改、删除、补充记忆内容
  • 就算系统崩了、索引坏了，只要 Markdown 文件还在，记忆就不会丢
  • 你可以用 Git 对记忆文件做版本管理，回溯、回滚、团队协作

两层记忆结构

记忆类型 存储格式 存储路径 产生方式 加载场景
精选长期记忆 MEMORY.md ~/.openclaw/workspace/ Agent 自动写入 / 手动编辑 仅主私人会话
每日记忆日志 memory/YYYY-MM-DD.md ~/.openclaw/workspace/memory/ Agent 自动追加 会话开始时读取今日和昨天
会话历史 .jsonl 文件 ~/.openclaw/agents/<agentId>/ 系统自动记录 当前对话上下文

MEMORY.md 只在主私人会话中加载，群聊等共享场景完全不会注入，保证了敏感信息的安全。它里面存储的是最高优先级的核心信息：

  • 用户的核心偏好：代码规范、接口设计风格、沟通习惯
  • 核心决策历史：项目的技术选型、架构设计决策、踩过的核心坑
  • Lessons Learned：过往项目里的经验教训

向量记忆搜索

虽然记忆以文件形式存储，但 OpenClaw 支持在 MEMORY.md 和 memory/*.md 上构建小型向量索引，实现语义搜索：

索引存储：每个 Agent 的 SQLite 文件位于 ~/.openclaw/memory/<agentId>.sqlite（可通过 agents.defaults.memorySearch.store.path 配置，支持 {agentId} 占位符）。

当 sqlite-vec 可用时，使用它加速 SQLite 中的向量搜索。本地模式使用 node-llama-cpp，远程模式支持 OpenAI 兼容端点。

记忆文件变更会被监视（带防抖），自动重建索引。搜索结果 MemorySearchResult 包含文件路径、起止行号、相关度分数、文本片段和来源等元数据，使 Agent 可以精确引用和读取记忆内容：

自动记忆刷新机制

新鲜度监控：监视 MEMORY.md 和 memory/*.md 的变更，带防抖自动重建索引。当会话接近自动压缩时，OpenClaw 会触发一个静默的 Agent 轮次，提醒模型在上下文被压缩之前写入持久记忆。

每个压缩周期仅刷新一次（在 sessions.json 中跟踪）。如果会话以 workspaceAccess: "ro" 或 "none" 的沙盒模式运行，则跳过刷新。

可选的 LanceDB 插件

除了内置的 memory-core 插件（两个排他性插件中默认选择），OpenClaw 还支持第三方 memory-lancedb 插件，使用面向多模态的 Lance 文件格式构建轻量级 LanceDB 数据库，提供更强大的长期记忆能力。

实验性扩展：部分社区实践探索了扩展 bank/ 目录，下设 world.md（客观事实）、experience.md（Agent 自身经历）、opinions.md（主观判断）以及 entities/（实体信息库）等更细粒度的记忆分类。

5.6 ACP 子 Agent 编排

源码位置：src/acp/

OpenClaw 实现了 ACP（Agent Control Protocol）协议，支持多 Agent 编排场景。ACP Server 作为子 Agent 的控制面，接受外部 Agent 的调用请求。

ACP 协议定义了标准的会话状态机：

  • idle：空闲等待
  • running：正在执行
  • waiting_input：等待用户输入
  • completed：执行完成
  • failed：执行失败

Control-Plane 负责管理子 Agent 的生命周期、资源分配和结果聚合。当主 Agent 遇到需要专业化处理的任务时，可以通过 ACP 协议委派给专门的子 Agent 执行。

六、关键技术亮点

6.1 车道式队列：默认串行，显式并行

这是 OpenClaw 工程哲学的核心体现。通过”车道式”（Lane-based）队列，保证每个会话的操作绝对串行，从根本上杜绝了：

  • 日志交织（不同消息的日志混在一起）
  • 状态冲突（并发操作导致的不一致）
  • 上下文串（不同对话的上下文互相污染）

不同 Lane 之间天然可以并行处理，充分利用多核资源。

6.2 上下文窗口守护与自动压缩

OpenClaw 实现了完整的三阶段上下文管理：

阶段 触发条件 动作
预警 token 接近软阈值 提醒 Agent 写入持久记忆
压缩 token 超过硬阈值 自动压缩会话历史
终止 token 达到极限 优雅终止，防止模型崩溃

压缩过程中，系统会保留关键的工具调用结果和决策历史，只压缩冗余的对话内容。这种有选择的压缩策略确保了 Agent 在长对话中不会丢失关键信息。

6.4 Lazy-Boundary 加载优化

源码位置：src/library.ts、src/entry.ts

OpenClaw 在加载策略上做了大量优化：

  • Lazy CLI 图：Commander 命令树按需加载，不阻塞启动
  • Lazy Provider 绑定：Provider 模块仅在需要时 import
  • Version/Help Fast Path：--version 和 --help 走预计算元数据，秒级响应
  • Compile Cache：Node.js 编译缓存，加速后续加载

这种按需加载的设计确保了 CLI 用户不承担库 API 的加载代价，库用户也不承担 CLI 的加载代价。

6.5 MCP 桥接机制

源码位置：src/tools/mcporter/

OpenClaw 通过 mcporter 桥接 MCP（Model Context Protocol），core 不内建 MCP 运行时，而是通过一个轻量级的桥接层将 MCP 工具转换为 OpenClaw 内部工具格式。

这种设计保持了核心的精简，同时兼容了 MCP 生态。新能力先进入 ClawHub（插件市场），不直接进入 core。

八、局限性与已知挑战

没有任何系统是完美的。OpenClaw 目前也存在一些局限性：

  1. 安全边界仍在完善：虽然设计了工具调用安全管线，但复杂场景下的权限控制还不够精细
  2. 记忆系统的向量搜索依赖外部 API：本地嵌入模型需要额外配置和计算资源
  3. 多 Agent 编排处于早期：ACP（Agent Control Protocol）子 Agent 编排功能还在迭代中
  4. Windows 支持有限：部分功能（如 Docker 沙箱、某些 channel 适配器）在 Windows 上的体验不如 macOS/Linux
  5. 插件生态碎片化：100+ 个 bundled 插件中，质量参差不齐，社区插件的标准尚未完全统一

九、总结

OpenClaw 并非一个简单的聊天机器人，而是一个工程化、可信赖的本地 AI 自动化平台。它通过精巧的架构设计——车道式队列、两层记忆系统、Skills 插件、多模型故障转移——在保障隐私和可靠性的前提下，将大模型的强大能力与本地系统的深度控制权结合起来。

它的工程价值体现在几个层面：

  • 架构层面：五层解耦，职责清晰，核心对扩展不可知
  • 设计层面：面向接口编程，插件化内核，本地优先
  • 实现层面：严格的分层纪律，按需加载优化，安全显式
  • 生态层面：100+ 插件，50+ Skills，29+ AI Provider，MIT 协议

对于希望掌控自己数字生活、探索个人 AI 助手可能性的开发者而言，OpenClaw 提供了一个极具参考价值的开源范本。它的代码仓库本身就是一本教科书，展示了如何在复杂的 AI Agent 场景中保持工程的纪律性和可维护性。
